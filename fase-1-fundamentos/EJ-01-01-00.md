## 📚 Fundamento

> [!info] Por qué este curso se hace en otra bóveda
> En este curso **rompes cosas a propósito**: borras ramas, provocas conflictos, deshaces commits, fuerzas un `push`. Y estás aprendiendo, así que también las romperás **sin querer**.
>
> Por eso el curso de Git **no toca tu bóveda real**. Vive entero en otra, `Boveda_Marko`, que creas hoy **dentro de tu carpeta `SOR`, al lado de `Boveda_SOR`**:
>
> ```
> 📁 SOR/                          ← la carpeta que creaste en la Bloque 0 · Fase 0.1
> │
> ├── Boveda_SOR/                  ← 🔒 tu trabajo real. EN ESTE CURSO NO SE TOCA
> │
> └── Boveda_Marko/                ← 🆕 la creas HOY (Paso 2)
>     ├── B0_Curso_Git/                ← 🆕 HOY (Paso 3): el material, para leerlo
>     ├── Bitacora/                    ← 🆕 HOY (Pasos 4 a 6): tus apuntes, lo que entregas
>     └── Manuales/                    ← en el EJ-01-01-03: donde se hacen los ejercicios
> ```
>
> Si algo explota en `Boveda_Marko`, **se borra entera y se vuelve a bajar de GitHub** ([🧯 Si lo rompes todo](../03_SI_LO_ROMPES_TODO.md)). Si explotara en `Boveda_SOR`, te llevarías los apuntes del trimestre.

> [!danger] 🛑 La regla de oro: `Boveda_Marko` es solo el contenedor
> **Ahí nunca se hace `git init`.** Los repositorios son las carpetas de dentro, cada una por separado. Si convirtieras la bóveda entera en repositorio, los de dentro quedarían unos dentro de otros —**Git dentro de Git**— y no podrías subirlos por separado. Es la misma regla de tu bóveda real.

> [!info] Por qué un técnico verifica antes de empezar
> En cualquier trabajo serio de sistemas, lo primero no es hacer: es **comprobar que se puede hacer**. Los pilotos repasan su lista antes de despegar **aunque el avión funcionara ayer**.
>
> Tres de las cinco comprobaciones de hoy ya las pasaste en los prerrequisitos, y **por eso mismo se repiten**: has cambiado de día, puede que de ordenador, y lo que funcionaba entonces puede no funcionar hoy.
>
> | # | Compruebo | Respondo a |
> | :--- | :--- | :--- |
> | 1 | `git --version` | ¿Está Git instalado y es lo bastante reciente? |
> | 2 | `git config` | ¿Sabe Git quién soy? ¿Con qué nombre firmo mis commits? |
> | 3 | `ssh -T git@github.com` | ¿Me reconoce GitHub sin pedirme la contraseña? |
> | 4 | Mi bitácora en GitHub | ¿Tengo dónde subir el trabajo? |
> | 5 | `git log` en mi bitácora | ¿He hecho un commit de verdad y ha llegado a GitHub? |
>
> Las tres primeras van **antes** de montar nada, porque sin ellas no podrías ni clonar. Las dos últimas van **después**, porque comprueban lo que acabas de montar.

> [!warning] El fallo nº1: el correo mal puesto
> Es el que más se repite y el más silencioso. Si `user.email` está mal escrito o es distinto del de tu cuenta de GitHub, **todo funciona**: puedes hacer commits y subirlos sin ningún error.
>
> Lo que pasa es que GitHub **no te reconoce como autor**: tus commits aparecen a nombre de un usuario fantasma, sin tu foto, y **no cuentan en tu perfil**. Cuando te das cuenta llevas dos meses y cuarenta commits huérfanos que ya no se arreglan.

> [!example] Vocabulario de esta práctica
> - **Bóveda contenedor:** una carpeta que agrupa repositorios pero que **no** es un repositorio.
> - **`pwd`:** *print working directory*. Dice en qué carpeta está la terminal.
> - **`git remote -v`:** dice a qué repositorio de GitHub está conectada la carpeta en la que estás.
> - **`--global`:** la configuración vale para **todos** tus repositorios, no solo el actual.
> - **Clave SSH:** la pareja de claves que te identifica ante GitHub sin contraseña.

### 🅰️ PARTE A — Comprueba que tu equipo puede trabajar

Abre una terminal cualquiera (**Git Bash** en Windows, **Terminal** en Linux). Para estas tres comprobaciones da igual en qué carpeta esté.

> [!example] Comprobación 1 — ¿Está Git instalado?
> ```bash
> git --version
> ```
> ✅ **Bien si** devuelve una versión **2.40 o superior**.
> ❌ **Si dice `command not found`:** no está instalado o has abierto el `cmd` en vez de Git Bash. → **Bloque 0 · Fase 0.2.1**, que trae la nota de instalación para Windows y Linux.

> [!example] Comprobación 2 — ¿Sabe Git quién eres? *(la importante)*
> ```bash
> git config --global user.name
> git config --global user.email
> ```
> ✅ **Bien si** salen tu nombre y tu correo, **y el correo es el mismo que el de tu cuenta de GitHub**.
>
> Compruébalo de verdad, no de memoria: entra en `github.com` → tu foto → **`Settings`** → **`Emails`**, y compara **carácter a carácter**.
>
> ❌ **Si están vacíos o mal:**
> ```bash
> git config --global user.name "Tu Nombre"
> git config --global user.email "el-mismo-de-github@ejemplo.com"
> ```
> → La explicación completa está en la **Bloque 0 · Fase 0.2.1**.
>
> > [!tip] 💡 Aprovecha y mira toda tu configuración
> > ```bash
> > git config --list
> > ```
> > Salen todos los ajustes activos. **Recuerda: se sale con `q`** — es el paginador, no se ha colgado.

> [!example] Comprobación 3 — ¿Te reconoce GitHub?
> ```bash
> ssh -T git@github.com
> ```
> ✅ **Bien si** responde `Hi TU-USUARIO! You've successfully authenticated...`
> *(Lo de "does not provide shell access" es normal y no es un error.)*
>
> ❌ **Si dice `Permission denied (publickey)`:** no tienes la clave SSH puesta en este equipo. → **Bloque 0 · Fase 0.2.2**.
> ❌ **Si se queda colgado y acaba en `timeout`:** el cortafuegos del centro está bloqueando el puerto 22. **Avísame**, tiene solución.

### 🅱️ PARTE B — Monta tu sitio de trabajo

> [!example] Paso 1 — Localiza tu carpeta `SOR` y abre la terminal SOBRE ella
> `SOR` es la carpeta que creaste en la **Bloque 0 · Fase 0.1** y que tiene dentro tu `Boveda_SOR`. Según lo que te salió entonces, está en **una** de estas rutas (la apuntaste aquel día):
>
> | Tu caso | Dónde está `SOR` |
> | :--- | :--- |
> | Windows, `Documentos` local | `C:\Users\TU-USUARIO\Documents\SOR` |
> | Windows, `Documentos` en OneDrive | `C:\Users\TU-USUARIO\SOR` |
> | Linux, con `Documentos` | `/home/tu-usuario/Documentos/SOR` |
> | Linux, sin `Documentos` | `/home/tu-usuario/SOR` |

> 1. Abre el **Explorador de archivos** y ve a esa ruta. Tienes que **ver la carpeta `Boveda_SOR`** dentro de `SOR`. Si no la ves, no estás en la carpeta correcta.
> 2. **Clic derecho en un hueco vacío**, dentro de `SOR` —al lado de `Boveda_SOR`, **no encima de ella**—:
>    - **Windows:** `Abrir Git Bash aquí` / `Git Bash Here`. En Windows 11 puede estar dentro de **`Mostrar más opciones`**.
>    - **Linux:** `Abrir en un terminal`.
> 3. Comprueba dónde has caído:
>    ```bash
>    pwd
>    ls
>    ```
>    ✅ **Sigue si** la ruta **termina en `/SOR`** y el `ls` muestra `Boveda_SOR`.
>    🛑 **Para si** la ruta termina en `Boveda_SOR` o en algo de dentro: te has pasado de carpeta. Cierra esa terminal y repite el punto 2.
>
> > [!tip] 💡 Si no te aparece la opción de clic derecho
> > Abre Git Bash como sea y escribe **una** de estas líneas, la de tu caso:
> > ```bash
> > cd ~/Documents/SOR      # Windows, Documentos local
> > cd ~/SOR                # Windows con OneDrive, o Linux sin Documentos
> > cd ~/Documentos/SOR     # Linux en español
> > ```
> > El `~` es "mi carpeta de usuario" (`C:\Users\TU-USUARIO` en Windows). Y comprueba con `pwd` y `ls` igualmente.

> [!example] Paso 4 — Crea la carpeta de tu bitácora y conviértela en repositorio
