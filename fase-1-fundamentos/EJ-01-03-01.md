## EJ-01-03-01 — Marko enmienda su último commit

> [!info] Situación
> Marko acaba de hacer un commit en su repositorio `Manuales` con el manual del NSG, pero se ha dado cuenta de que olvidó actualizar el `README.md` (el índice) para enlazar el nuevo apartado. **NO** ha hecho push todavía. Quiere que ese arreglo entre en el **mismo** commit, sin crear uno nuevo.

- **🎯 Objetivo real:** usar `git commit --amend` para corregir el último commit (mensaje o contenido) sin generar un commit extra.
- **🧩 Problema que resuelve:** sin `--amend`, Marko tendría dos commits: uno parcial y otro "olvidé un archivo". Histórico ruidoso.

---

## 📚 Fundamento

> [!info] Antes de empezar: rehacer la última foto
> `git commit --amend` **rehace el último commit**: coge lo que había, le suma lo que tengas ahora en la sala de espera (o cambia solo el mensaje) y lo deja como **un único commit**. Es como repetir una foto que salió movida, en lugar de pegar una segunda foto al lado.

> [!abstract] Idea clave: solo para lo que aún NO has compartido
> `--amend` **cambia el commit** (le da un hash nuevo). Eso está bien si el commit todavía vive solo en tu ordenador. Pero si ya lo **pusheaste** a una rama que otros usan, cambiarlo les rompe el histórico. Regla: **enmienda solo lo que aún no has subido**.

> [!example] Vocabulario de esta práctica
> - **`git commit --amend`:** rehace el último commit.
> - **Hash:** identificador único del commit; al enmendar, **cambia**.
> - **Histórico limpio:** sin commits "parche" del tipo "se me olvidó...".

---

## 🛠️ Procedimiento
Trabaja dentro de `Manuales/` (todos los ficheros están en ese repositorio).

> [!example] Paso 1 — Corrige el archivo que olvidaste
> Edita `README.md` y añade una línea que enlace el manual del NSG. Guarda.

> [!example] Paso 2 — Prepáralo
> ```
> git add README.md
> ```

> [!example] Paso 3 — Enmienda el último commit
> ```
> git commit --amend -m "EJ-01-03-01 · Manual NSG (incluye enlace en el índice README)"
> ```

> [!example] Paso 4 — Comprueba el histórico
> ```
> git log --oneline
> ```
> Debe aparecer **UN** commit (el enmendado), no dos.

---

## 🚩 Errores y verificación

> [!danger] NO enmiendes algo que ya has pusheado
> Si el commit ya está en GitHub en una rama compartida, `--amend` cambia su hash y **rompe el histórico** de quien ya lo tenía. Enmienda solo commits que aún viven solo en tu equipo.

> [!warning] Truco útil
> Si solo quieres **cambiar el mensaje** (sin añadir archivos), no hace falta `git add`: directamente `git commit --amend -m "nuevo mensaje"`.

> [!success] ✅ Verificación: ¿está bien hecho?
> - `git log --oneline` muestra el commit con el mensaje nuevo.
> - **No** hay commit duplicado del tipo "olvidé...".

> [!question] Comprueba que lo has entendido
> Responde en tu bitácora:
> 1. ¿Qué hace `git commit --amend`?
> 2. ¿Por qué NO se debe enmendar un commit ya pusheado y compartido?
> 3. Si solo quieres cambiar el mensaje, ¿necesitas hacer `git add`?

## ✅ Entregables y cierre

- **Entregable GitHub:** aún no (el push se hace en un ejercicio posterior).
- **Entregable bóveda:** `README.md` actualizado y recogido en el commit enmendado.
- **Criterio de éxito:** un solo commit con el mensaje nuevo; sin duplicados.

> [!summary] 🎓 Qué has aprendido en este ejercicio
> - A **rehacer el último commit** con `git commit --amend` para mantener el histórico limpio.
> - Que enmendar **cambia el hash**, así que solo se hace con commits **no compartidos**.
> - Que se puede cambiar solo el mensaje, o también el contenido.
