## EJ-02-03-02 — Marko hace un cherry-pick

> [!info] Situación
> Carlos ha hecho un commit en su rama `experimentos/configuracion-fail2ban` que tiene **UN** comando útil que Marko quiere copiar a su rama, pero **NO** el resto del experimento de Carlos.

- **🎯 Objetivo real:** usar `git cherry-pick` para copiar **un commit concreto** de otra rama sin traer todo lo demás.
- **🧩 Problema que resuelve:** sin cherry-pick, Marko copiaría el código a mano y rehacería el commit, perdiendo los metadatos (autoría, fecha).

---

## 📚 Fundamento

> [!info] Antes de empezar: "coger una cereza"
> A veces no quieres fusionar una rama entera: solo te interesa **un commit suelto** de ella. **`git cherry-pick <hash>`** copia **ese** commit (y solo ese) a tu rama actual. Es como coger una única cereza del árbol, en vez de todo el ramo.

> [!abstract] Idea clave: mismo contenido, nuevo hash
> El commit copiado tiene el **mismo cambio**, pero un **hash distinto** (es una copia nueva). El original sigue en su sitio.

> [!example] Vocabulario de esta práctica
> - **`git cherry-pick <hash>`:** copia un commit concreto a la rama actual.
> - **Hash:** identificador del commit que quieres copiar.
> - **`--continue`:** sigue tras resolver un conflicto de cherry-pick.

---

## 🛠️ Procedimiento
Para practicar, primero simulamos el commit de Carlos.

> [!example] Paso 1 — Crea la rama y el commit "de Carlos"
> ```
> git switch -c experimentos/fail2ban-carlos
> ```
> Crea el archivo:
>
> *🐧 Git Bash / Linux*
> ```bash
> touch 05_seguridad/fail2ban_config.md
> ```
> *🪟 PowerShell*
> ```powershell
> New-Item 05_seguridad\fail2ban_config.md -ItemType File
> ```
> Escribe algo dentro y commitea:
> ```
> git add 05_seguridad/fail2ban_config.md
> git commit -m "EJ-02-03-02-prep · [Carlos] Configuración fail2ban"
> ```

> [!example] Paso 2 — Anota el hash de ese commit
> ```
> git log --oneline -1
> ```

> [!example] Paso 3 — Vuelve a `develop`
> ```
> git switch develop
> ```

> [!example] Paso 4 — Copia SOLO ese commit
> ```
> git cherry-pick <hash-anotado>
> ```
> Si hay conflicto: resuélvelo, `git add`, `git cherry-pick --continue`.

> [!example] Paso 5 — Comprueba el resultado
> ```
> git log --oneline
> ```
> Aparece el commit copiado, con **nuevo** hash.

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Copias el hash mal | Cherry-pick del commit equivocado | Copia el hash con cuidado desde `git log --oneline`. |
> | Conflicto y no sabes seguir | Te quedas a medias | Resuelve, `git add`, `git cherry-pick --continue`. |

> [!success] ✅ Verificación: ¿está bien hecho?
> - El archivo `05_seguridad/fail2ban_config.md` está también en `develop`.
> - `git log` refleja el commit copiado con hash nuevo.

> 3. ¿Cuándo usarías cherry-pick en vez de un merge?

## ✅ Entregables y cierre

- **Entregable GitHub:** push tras el cherry-pick.
- **Entregable bóveda:** `05_seguridad/fail2ban_config.md` presente también en `develop`.
- **Criterio de éxito:** el archivo está en `develop` y `git log` lo refleja.

> [!summary] 🎓 Qué has aprendido en este ejercicio
> - A copiar **un commit concreto** de otra rama con `git cherry-pick`.
> - Que el commit copiado conserva el cambio pero cambia de **hash**.
> - Cuándo conviene (traer una mejora suelta sin fusionar toda la rama).
