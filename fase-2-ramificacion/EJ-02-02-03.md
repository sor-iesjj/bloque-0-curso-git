## EJ-02-02-03 — Marko hace una "release": de `develop` a `main`

> [!info] Situación
> Lucía valida el trabajo del mes. Marko publica la versión `v1.0.0`: pasa el contenido validado de `develop` a `main`.

- **🎯 Objetivo real:** aprender el patrón "release": merge `develop → main` + **tag** de versión.
- **🧩 Problema que resuelve:** sin tags, no hay forma de referirse a "la versión 1.0" sin recordar hashes.

---

## 📚 Fundamento

> [!info] Antes de empezar: qué es una "release" y un "tag"
> Una **release** es el momento en que lo validado en `develop` pasa al escaparate `main`. Para poder **nombrar** esa versión, se le pone un **tag**: una etiqueta con un nombre (`v1.0.0`) sobre un commit concreto. Así puedes decir "vuelve a la v1.0.0" sin recordar el hash.

> [!abstract] Idea clave: versionar con SemVer
> Las versiones se numeran `MAJOR.MINOR.PATCH` (versionado semántico): subes **PATCH** por arreglos pequeños, **MINOR** por cosas nuevas compatibles, y **MAJOR** por cambios grandes. Empezamos en `v1.0.0`.

> [!example] Vocabulario de esta práctica
> - **Tag:** etiqueta con nombre sobre un commit.
> - **Tag anotado (`-a`):** lleva autor, fecha y mensaje (el que usamos).
> - **SemVer:** `MAJOR.MINOR.PATCH`.

---

## 🛠️ Procedimiento

> [!example] Paso 1 — Cámbiate a `main` y actualízala
> ```
> git switch main
> git pull
> ```

> [!example] Paso 2 — Fusiona `develop` en `main`
> ```
> git merge develop
> ```

> [!example] Paso 3 — Etiqueta la versión
> ```
> git tag -a v1.0.0 -m "Versión 1.0: repositorio de manuales con estructura inicial + manuales Ubuntu y Samba"
> ```

> [!example] Paso 4 — Sube todo, incluido el tag
> ```
> git push
> git push --tags
> ```

> [!example] Paso 5 — Compruébalo en GitHub
> Ve a la pestaña **"Releases"** (o "Tags"): debe aparecer `v1.0.0`.

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Creas un tag "ligero" (sin `-a`) | No lleva metadatos | Usa siempre `git tag -a ... -m "..."`. |
> | Haces `git push` pero olvidas los tags | El tag no sube | Añade `git push --tags`. |

> [!success] ✅ Verificación: ¿está bien hecho?
> - `git tag` lista `v1.0.0`.
> - En GitHub aparece como release/tag.

> 2. ¿Para qué sirve un tag y qué ventaja tiene frente a recordar un hash?
> 3. ¿Qué significan las tres partes de `v1.0.0`?

## ✅ Entregables y cierre

- **Entregable GitHub:** tag `v1.0.0` visible.
- **Entregable bóveda:** sin cambios nuevos.
- **Criterio de éxito:** `git tag` muestra `v1.0.0` y en GitHub aparece como release.

> [!summary] 🎓 Qué has aprendido en este ejercicio
> - El patrón **release**: fusionar `develop → main` y **etiquetar** la versión.
> - Qué es un **tag anotado** y cómo subirlo (`git push --tags`).
> - El versionado **SemVer** (`MAJOR.MINOR.PATCH`).
