## 📚 Fundamento

> [!info] Antes de empezar: git-flow junta todo lo que sabes
> **git-flow** es un flujo con ramas de roles fijos: `feature/*` (construir), `develop` (integrar), `release/*` (preparar una versión), `main` (estable) y `hotfix/*` (urgencias). Ya conoces cada pieza; git-flow es el **mapa** que las ordena.

> [!abstract] Idea clave: git-flow vs GitHub Flow
> - **git-flow:** completo (con `develop` y `release`), bueno para versiones planificadas.
> - **GitHub Flow:** simple (solo `main` + features), bueno para entregar continuamente.
> No hay uno "mejor": depende del equipo. Aquí practicas el completo para conocerlo.

> [!example] Vocabulario de esta práctica
> - **Rama `release/*`:** rama temporal para **rematar** una versión (solo bugfixes, no features nuevas).
> - **git-flow:** el flujo completo con roles de rama fijos.

> [!example] Paso 2 — Abre la rama de release
> ```

> [!example] Paso 3 — En la release, SOLO bugfixes
> En `release/v1.2.0` no se añaden features nuevas: solo se pulen detalles. Haz un commit pequeño de ajuste.

> [!example] Paso 4 — Release → main + tag
> Abre PR `release → main`, fusiónalo, y etiqueta:
> ```
> git switch main
> git pull
> git tag -a v1.2.0 -m "Release 1.2.0"
> git push --tags
> ```

> [!example] Paso 5 — Sincroniza también con develop y limpia
> ```
> git switch develop
> git merge main
> git push
> git branch -d release/v1.2.0
> ```

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Metes features nuevas en `release/*` | La versión no se estabiliza | En `release/` solo bugfixes. |
> | Olvidas fusionar la release en `develop` | `develop` pierde los ajustes | Fusiona `main`→`develop` tras la release. |

> [!success] ✅ Verificación: ¿está bien hecho?
> - El tag `v1.2.0` existe.
> - `develop` y `main` tienen el mismo contenido tras la release.
