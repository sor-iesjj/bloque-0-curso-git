- **🎯 Objetivo real:** adoptar **SemVer** (`MAJOR.MINOR.PATCH`) para versionar el repositorio de manuales.
- **🧩 Problema que resuelve:** sin SemVer, los números de versión son arbitrarios y no comunican nada.

---

## 📚 Fundamento

> [!info] Antes de empezar: cada número cuenta algo
> **SemVer** da significado a los tres números `MAJOR.MINOR.PATCH`:
> - **MAJOR** (`X.0.0`): cambio **incompatible** (por ejemplo, reorganizar todas las carpetas y cambiar rutas).
> - **MINOR** (`1.X.0`): algo **nuevo** que no rompe nada (un manual nuevo).
> - **PATCH** (`1.1.X`): un **arreglo** pequeño (un typo, un comando mal).

> [!abstract] Idea clave: la versión avisa del riesgo
> Solo con ver el número, quien usa tu trabajo sabe **cuánto ha cambiado**: un PATCH es seguro, un MAJOR avisa de que "algo gordo cambió". Comunica sin leer nada más.

> [!example] Vocabulario de esta práctica
> - **SemVer:** `MAJOR.MINOR.PATCH`.
> - **Incompatible:** cambio que rompe cómo se usaba antes.

> [!example] Paso 1 — Documenta la política
> Crea `00_infraestructura/versionado.md`:
> ```
> # Política de versionado (SemVer 2.0.0)
> - MAJOR (X.0.0): cambios incompatibles (ej. reorganización completa de carpetas).
> - MINOR (1.X.0): funcionalidad nueva compatible (ej. añadir manual nuevo).
> - PATCH (1.1.X): bugfix compatible (ej. corregir typo o comando).
>
> ## Ejemplos
> - v1.0.0 → v1.0.1: typo corregido.
> - v1.0.1 → v1.1.0: añadido manual VPN.
> - v1.1.0 → v2.0.0: reorganizadas carpetas (las rutas cambian).
> ```

> [!example] Paso 2 — Súbelo
> ```
> git add 00_infraestructura/versionado.md
> git commit -m "EJ-04-03-04 · Política de versionado SemVer"
> git push
> ```

> [!example] Paso 3 — Aplícalo en la próxima release
> **Mira primero qué versiones ya existen**, que es lo que haría cualquiera antes de etiquetar:
> ```
> git tag -l
> ```
>
> Verás `v1.1.0`, `v1.1.1` y `v1.2.0` — esta última la cerraste tú en el **EJ-04-02-01**. Así que la siguiente **no puede ser `v1.2.0` otra vez**: añadir el manual de VPN es algo nuevo y compatible, o sea **MINOR**, o sea `v1.3.0`:
> ```
> git tag -a v1.3.0 -m "v1.3.0: añadido manual VPN WireGuard"
> git push --tags
> ```
>
> > [!warning] ⚠️ Si escribes `v1.2.0` te saldrá `fatal: tag 'v1.2.0' already exists`
> > Y está bien que salga: **Git no te deja reescribir una versión ya publicada.** Una etiqueta es un contrato — alguien puede haberse descargado ya ese `v1.2.0`.
> >
> > **Por eso `git tag -l` va SIEMPRE antes de `git tag -a`.** Es un reflejo, como el `pwd` antes de un `rm`.
