## EJ-04-02-02 — Marko usa `git reflog` para recuperar trabajo perdido

> [!info] Situación
> Marko hizo `git reset --hard` por error y perdió 3 commits. Lucía: *"Tranquilo, Git lo recuerda todo durante 90 días. Usa `reflog`."*

- **🎯 Objetivo real:** recuperar commits "perdidos" usando el **reflog** (el registro local de movimientos de `HEAD`).
- **🧩 Problema que resuelve:** sin reflog, un `reset --hard` parece irreversible. Con reflog, casi siempre se recupera.

---

## 📚 Fundamento

> [!info] Antes de empezar: Git tiene una "papelera" con memoria
> Cada vez que `HEAD` se mueve (un commit, un reset, un cambio de rama…), Git lo anota en el **reflog**. Aunque un `reset --hard` **parezca** haber borrado tus commits, el reflog **recuerda** dónde estaban. Es tu red de seguridad ante los accidentes.

> [!abstract] Idea clave: casi nada se pierde de verdad
> Mientras no pasen ~90 días, esos commits "perdidos" siguen existiendo. Solo hay que **encontrar su hash** en el reflog y volver a él.

> [!example] Vocabulario de esta práctica
> - **`git reflog`:** lista los movimientos recientes de `HEAD`.
> - **`HEAD@{N}`:** una posición anterior de `HEAD`.
> - **Local:** el reflog vive solo en tu equipo (no se clona).

---

## 🛠️ Procedimiento
Dentro de `Manuales/`.

> [!example] Paso 1 — Provoca el "desastre" (a propósito)
> Haz 3 commits de prueba y luego:
> ```
> git reset --hard HEAD~3
> ```
> Los 3 commits desaparecen de `git log`. 😱

> [!example] Paso 2 — Mira el reflog
> ```
> git reflog
> ```
> Lista TODAS las posiciones recientes de `HEAD`, incluidas las de antes del reset.

> [!example] Paso 3 — Identifica el punto al que volver
> Localiza el hash (o `HEAD@{N}`) **anterior** al `reset --hard`.

> [!example] Paso 4 — Recupera
> ```
> git reset --hard <hash>
> ```

> [!example] Paso 5 — Verifica
> ```
> git log --oneline
> ```
> Los 3 commits están de vuelta. 🎉

---

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Esperas encontrar el reflog en otro PC | Es LOCAL, no se clona | Recupera en el mismo equipo donde ocurrió. |
> | Tardas más de 90 días | Las entradas caducan | Recupera cuanto antes. |

> [!success] ✅ Verificación: ¿está bien hecho?
> - Los 3 commits aparecen de nuevo en `git log`.

> [!question] Comprueba que lo has entendido
> Responde en tu bitácora:
> 1. ¿Qué guarda el reflog?
> 2. ¿Por qué un `reset --hard` no es tan irreversible como parece?
> 3. ¿El reflog se comparte al clonar el repo?

## ✅ Entregables y cierre

- **Entregable GitHub:** ninguno (el desastre no se pusheó).
- **Entregable bóveda:** estado restaurado.
- **Criterio de éxito:** los 3 commits vuelven a `git log`.

> [!summary] 🎓 Qué has aprendido en este ejercicio
> - Que el **reflog** es la red de seguridad de Git ante accidentes.
> - A **recuperar** commits tras un `reset --hard` con su hash.
> - Que el reflog es **local** y caduca (~90 días).
