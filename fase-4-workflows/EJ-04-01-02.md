## EJ-04-01-02 — Marko publica una Release en GitHub

> [!info] Situación
> Lucía: *"Quiero que la versión `v1.1.0` aparezca como Release oficial con notas, para que cualquiera pueda descargar el repositorio en ese estado."*

- **🎯 Objetivo real:** convertir un **tag** en una **Release** con notas y archivos descargables.
- **🧩 Problema que resuelve:** un tag es algo técnico; una Release es pública, con notas humanas y descargas.

---

## 📚 Fundamento

> [!info] Antes de empezar: tag vs Release
> Un **tag** es un marcador interno de Git. Una **Release** de GitHub es la versión "de cara al público": coge un tag y le añade **título**, **notas** (qué hay de nuevo) y **descargas** (GitHub adjunta el ZIP/TAR del repo en ese punto). Un tag es para técnicos; una Release, para cualquiera.

> [!abstract] Idea clave: las notas son para personas
> Las notas de una Release las lee gente que quizá no conoce el detalle técnico. Escribe **novedades** en lenguaje claro: qué se ha añadido, qué ha cambiado, qué viene después.

> [!example] Vocabulario de esta práctica
> - **Release:** versión publicada con notas y descargas.
> - **Pre-release:** versión no definitiva (se marca aparte).
> - **Assets:** los archivos que GitHub adjunta (ZIP/TAR).

---

## 🛠️ Procedimiento

> [!example] Paso 1 — Empieza una Release nueva
> En GitHub: **Releases → "Draft a new release"**.

> [!example] Paso 2 — Elige el tag y el título
> - **Choose tag:** `v1.1.0`
> - **Release title:** `v1.1.0 — Manuales SSH y Samba`

> [!example] Paso 3 — Escribe las notas
> ```
> ## Novedades
> - Manual de instalación SSH (EJ-03-01-02)
> - Manual de Samba AD DC completado (EJ-02-02-02)
> - Configuración de NSG documentada (EJ-01-02-01)
>
> ## Cambios técnicos
> - .gitignore protege secretos.
> - CODEOWNERS asignados por área.
>
> ## Próxima versión
> v1.2.0 incluirá manuales de VPN WireGuard y firewall.
> ```

> [!example] Paso 4 — Publícala
> Pulsa **"Publish release"**. GitHub adjunta automáticamente el ZIP y el TAR.GZ del repo en ese tag.

---

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | No existe el tag `v1.1.0` | No puedes elegirlo | Crea el tag antes (EJ-04-01-01). |
> | Notas vacías o técnicas | Nadie entiende la versión | Escribe novedades claras para personas. |

> [!success] ✅ Verificación: ¿está bien hecho?
> - En GitHub, "Releases" muestra `v1.1.0` publicada.

## ✅ Entregables y cierre

- **Entregable GitHub:** Release `v1.1.0` publicada.
- **Entregable bóveda:** sin cambios.
- **Criterio de éxito:** "Releases" muestra `v1.1.0`.

> [!summary] 🎓 Qué has aprendido en este ejercicio
> - A convertir un **tag** en una **Release** con notas y descargas.
> - Que las notas se escriben **para personas**, no solo para técnicos.
> - Que GitHub adjunta el ZIP/TAR del repo automáticamente.
