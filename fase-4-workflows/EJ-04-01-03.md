## EJ-04-01-03 — Marko crea una rama hotfix de emergencia

> [!info] Situación
> A las 9 de la noche, Carlos llama: *"Marko, el manual de Samba que está en `main` tiene un error en el comando de provisión. Si alguien lo usa esta noche, va a romper el dominio. Hay que arreglarlo YA."* Marko no puede esperar al ciclo normal `develop → main`.

- **🎯 Objetivo real:** crear una rama `hotfix/*` **directamente desde `main`**, arreglar, y fusionar a `main` **Y** a `develop`.
- **🧩 Problema que resuelve:** sin hotfix, un bug crítico esperaría al siguiente release. Inaceptable si algo está roto ahora.

---

## 📚 Fundamento

> [!info] Antes de empezar: la salida de emergencia
> El flujo normal es `feature → develop → main`. Pero una **urgencia crítica** en `main` no puede esperar a todo ese recorrido. El **hotfix** es la salida de emergencia: se parte **directamente de `main`**, se arregla, y se mete a `main` ya.

> [!danger] Lo más importante: mete el hotfix TAMBIÉN en `develop`
> El error más típico y más grave: arreglas `main` pero **olvidas** llevar el fix a `develop`. Resultado: en el **siguiente release**, `develop` (que no tenía el arreglo) **reintroduce el bug**. Un hotfix se fusiona **en las dos** ramas.

> [!example] Vocabulario de esta práctica
> - **Hotfix:** arreglo urgente que parte de `main`.
> - **PATCH:** el último número de la versión (`v1.1.1`); sube por un bugfix.

---

## 🛠️ Procedimiento
Dentro de `Manuales/`.

> [!example] Paso 1 — Parte de `main` actualizado
> ```
> git switch main
> git pull
> ```

> [!example] Paso 2 — Crea la rama hotfix
> ```
> git switch -c hotfix/comando-provision-samba
> ```

> [!example] Paso 3 — Corrige y sube
> Edita `02_active_directory/samba_ad_dc.md` y corrige el comando. Luego:
> ```
> git add 02_active_directory/samba_ad_dc.md
> git commit -m "EJ-04-01-03 · Hotfix: corregido comando de provisión Samba"
> git push -u origin hotfix/comando-provision-samba
> ```

> [!example] Paso 4 — PR urgente contra `main` y etiqueta el PATCH
> Abre el PR contra `main`, fusiónalo, y etiqueta la versión de arreglo:
> ```
> git switch main
> git pull
> git tag -a v1.1.1 -m "Hotfix: comando provisión Samba"
> git push --tags
> ```

> [!example] Paso 5 — ⚠️ CRÍTICO: mete el fix también en `develop`
> ```
> git switch develop
> git merge main
> git push
> ```

---

## 🚩 Errores y verificación

> [!danger] No olvides `develop`
> Si te saltas el Paso 5, el bug **vuelve** en el próximo release. Es el fallo más común con los hotfix.

> [!warning] Otros errores típicos
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Partes de `develop` en vez de `main` | El hotfix arrastra cosas a medias | Un hotfix parte SIEMPRE de `main`. |
> | Subes MINOR/MAJOR por un bugfix | Versionado incoherente | Un arreglo sube el **PATCH** (`v1.1.1`). |

> [!success] ✅ Verificación: ¿está bien hecho?
> - El tag `v1.1.1` existe.
> - El comando arreglado está en `main` **Y** en `develop`.

> [!question] Comprueba que lo has entendido
> Responde en tu bitácora:
> 1. ¿De qué rama parte un hotfix y por qué?
> 2. ¿Por qué hay que fusionarlo también en `develop`?
> 3. ¿Qué número de versión sube un bugfix?

## ✅ Entregables y cierre

- **Entregable GitHub:** hotfix fusionado en `main` y `develop`; tag `v1.1.1`.
- **Entregable bóveda:** manual de Samba corregido en ambas ramas.
- **Criterio de éxito:** `v1.1.1` existe y el arreglo está en `main` y `develop`.

> [!summary] 🎓 Qué has aprendido en este ejercicio
> - El flujo **hotfix**: arreglo urgente partiendo de `main`.
> - Que un hotfix se fusiona en **`main` y `develop`** (o el bug vuelve).
> - Que un bugfix sube el número **PATCH** de la versión.
